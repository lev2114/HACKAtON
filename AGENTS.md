# AGENTS.md — инструкции для ИИ-агентов в этом репозитории

Это каноничный файл с инструкциями для любого ИИ-кодинг-агента, который
работает в этом репозитории (Claude Code, Codex/ChatGPT, Antigravity —
у нас в команде используются все три, у каждого человека свой). Если твой
агент умеет читать `AGENTS.md` автоматически — он уже сделал это. Если нет
— человек должен явно попросить: "прочитай AGENTS.md, CONTEXT.md и
последние записи в UPDATES.md перед началом работы".

Хакатон идёт 2 дня, нас трое, пишем на трёх разных агентах одновременно в
один git-репозиторий. Единственный способ не наступать друг другу на
голову — дисциплинированно читать/писать файлы из раздела 1 ниже.

## 1. Перед началом ЛЮБОЙ работы — прочитай в этом порядке

1. `AGENTS.md` (этот файл) — правила.
2. `CONTEXT.md` — что сейчас является правдой: архитектура, стек, статус.
3. `PROTOCOL.md` — формат сообщений клиент↔сервер (если трогаешь сеть).
4. Верхние 10-15 записей `UPDATES.md` — что произошло недавно, что могло
   поменяться после твоего последнего коммита.
5. `TASKS.md` — что уже занято другими, что свободно.

Если видишь, что `CONTEXT.md` врёт по сравнению с реальным кодом (кто-то
забыл обновить) — поправь `CONTEXT.md`, не молчи об этом.

## 2. Перед тем как закоммитить

1. Сделай `git pull` — мы часто коммитим мелко и параллельно.
2. Если менял(а) архитектуру, стек, формат сообщений или статус
   компонента — обнови `CONTEXT.md` (и `PROTOCOL.md`, если менял формат
   сообщений) **в том же коммите**.
3. Добавь новую запись **в начало** `UPDATES.md` (см. формат там).
4. Если закрыл(а)/взял(а) задачу — обнови `TASKS.md`.
5. Коммить мелкими, логически законченными кусками, не "работа за весь
   день одним коммитом" — проще разбирать конфликты и читать историю.

Формат коммит-сообщений: `тип(область): что сделано` —
`feat(client)`, `fix(server)`, `feat(ai)`, `docs`, `chore`. Область — одна
из: `client`, `server`, `ai`, `world`, `docs`.

## 3. Правила по коду

**Go (`/server`)**:
- Стандартный `gofmt`, никаких внешних линтеров не настраивали — но перед
  коммитом прогоняй `go build ./...` и `go vet ./...`, это должно проходить
  всегда.
- Ошибки оборачивай (`fmt.Errorf("...: %w", err)`), не глушить молча.
- Не плоди новые абстракции/интерфейсы "на будущее" — у нас 2 дня,
  конкретный код для конкретной задачи.
- Вся сеть (WS-сообщения) — только через `internal/httpapi`, формат — как
  в `PROTOCOL.md`. Если нужен новый тип сообщения — опиши его в
  `PROTOCOL.md` до/вместе с реализацией.

**JS (`/client`)**:
- Чистый JS (ES-модули), **без TypeScript и без фреймворка** — так
  договорились, не предлагай React/Vue/TS посреди хакатона, это замена
  архитектуры, а не фича.
- three.js — напрямую, без доп. обёрток типа react-three-fiber.
- Любое новое сетевое сообщение — сначала добавь обработчик в `net.js`
  и пропиши в `PROTOCOL.md`.

**world-data (`/world-data/*.json`)**:
- Контент (комнаты/NPC/факты) можно и нужно расширять свободно — это не
  архитектурное изменение. Если меняешь **структуру** JSON (новые поля,
  другие ключи) — это меняет контракт `internal/world`, значит правь и
  Go-код загрузки, и `CONTEXT.md`.

## 4. Чего не делать

- Не коммитить `node_modules/`, `client/dist/`, `server/station.db`,
  `*.exe`, `*.log` — они в `.gitignore`, если видишь их в `git status`,
  проверь, что не добавляешь руками.
- Не делать `git push --force` и не переписывать историю (`rebase -i`,
  `commit --amend` на уже запушенном) — мы все тянем из одной ветки,
  force-push чужому сломает дерево на хакатоне, когда нет времени чинить.
- Не менять стек (Go / three.js / SQLite) без явного решения всей команды
  — это зафиксировано в `CONTEXT.md` сознательно.
- Не делать сетевые вызовы к внешним API из серверного кода, кроме
  локального Ollama (`localhost:11434`) — на демо интернета не будет,
  всё остальное обязано работать и без него.

## 5. Как быстро проверить, что ничего не сломал

```bash
# сервер
cd server && go build ./... && go vet ./...

# клиент
cd client && npm run build
```

Если есть время — ручной smoke-тест: поднять сервер (`go run ./cmd/server`),
открыть клиент (`npm run dev`), залогиниться, зайти в комнату, поговорить с
NPC, открыть второй клиент другим именем и убедиться, что игроки видят
движения друг друга в одной комнате.

## 6. Если застрял(а) / решение неочевидно

Если решение явно архитектурное (новый тип данных, смена протокола,
новый способ синхронизации) — не решай это в одиночку молча, оставь это
явно видимым: либо вопрос в `TASKS.md` рядом с задачей, либо сообщение
человеку. Мелкие технические решения (как назвать функцию, куда положить
файл) — решай сам(а) по аналогии с существующим кодом.
