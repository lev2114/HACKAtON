## 1. Что мы делаем

Хакатон-задание: браузерная 3D-виртуальная реальность (three.js), с
мультиплеером по LAN/WiFi, серверной подгрузкой мира по позиции игрока
(клиент кеширует ≤10% всего мира), двунаправленным WebSocket-каналом после
авторизации, персистентным состоянием игроков и ИИ-NPC с индивидуальностью
и памятью о конкретном игроке. ИИ считается только локально — на демо
компьютеры отключены от интернета. Полный текст задания — у организаторов,
сюда не копируем целиком, чтобы не разъезжалось с источником.

**Наша концепция:** космическая станция **"Шаролёт"**. В данных есть 9 отсеков вокруг центрального вестибюля, в каждом отсеке и в lobby — NPC
(персонаж "Смешариков"), который рассказывает научные факты о космосе по
своей теме. Социальный/образовательный смысл — научпоп про космос,
подаваемый через знакомых персонажей.

Тема и состав персонажей — утверждены, но считаются **дорабатываемыми**:
если по ходу хакатона решите поменять тему комнаты или факты — правьте
`world-data/*.json` и эту секцию, архитектура ниже не завязана на конкретный
контент.

### Комнаты и NPC (сейчас в `world-data/`)

| room id | название / дверь в lobby | NPC |
|---|---|---|
| `hub` | Центральный вестибюль, 9 дверей | Крош |
| `room_medbay` | Медблок / Medbay | Совунья |
| `room_rockets` | Механический отсек / Mechanical Bay | Пин |
| `room_greenhouse` | Биолаборатория / Bio Lab | Копатыч |
| `room_chemistry` | Химическая лаборатория / Chem Lab | Лосяш |
| `room_radio` | Радиорубка / Radio Room | Кар-Карыч |
| `room_stars` | Обсерватория / Planetarium | Лосяш |
| `room_library` | Библиотека / Library | Ёжик |
| `room_gravity` | Скафандровый отсек / Spacesuit Room | Нюша |
| `room_dining` | Столовая / Cafeteria | Совунья |

Все 10 комнат используют GLB. Стартовый `hub` — `starling-lobby-9-doors.glb`;
его девять дверей связаны с соответствующими отсеками, каждый имеет обратный
проход в lobby. Старые id биолаборатории и скафандрового отсека сохранены.
Добавлены десять экземпляров NPC по распределению команды. Лосяш и Совунья
имеют отдельные id в разных комнатах и тематические factBank. Все персонажи
используют GLB из пользовательских файлов, включая rigged-модель Ёжика
`yozhik-character.glb` в библиотеке.
Бараш из вложений не подключён — его нет в запрошенном списке.
Лестница lobby ведёт на галерею высотой 3.806 м; клиент использует настоящие
поверхности ступеней и галереи, блокирует стены, мебель и края. Та же коллизия включена во всех десяти
комнатах; поверхности пола выбираются по именам GLB, NPC имеют круглый
коллайдер. Тонкая мебель проверяется на её собственной высоте. Автоматический
шаг вверх до 0.24 м, вниз до 0.28 м; прыжков/свободного падения нет.

Каждый NPC в `facts.json` имеет 4-6 фактов разного уровня сложности —
это заготовка, контент можно и нужно расширять (больше фактов = NPC дольше
не повторяется и правдоподобнее "помнит", что уже рассказал).

## 2. Технологический стек (зафиксировано, не пересматриваем без причины)

- **Клиент**: чистый JS + **three.js**, сборка через **Vite**. Никакого
  TypeScript (договорились не усложнять на 2 дня).
- **Сервер**: **Go**. WebSocket — `gorilla/websocket`. БД — SQLite через
  `modernc.org/sqlite` (чистый Go, без cgo — не будет проблем со сборкой
  на Windows без установленного gcc).
- **ИИ**: гибрид. Конечный автомат + база фактов на сервере (надёжный
  офлайн-safe базовый слой) + опционально **Ollama /api/chat** (локальная
  LLM, по умолчанию `qwen2.5:7b`) с полноценной памятью диалога (до 3
  последних реплик на пару игрок-NPC) и своим системным промптом-характером
  на каждого персонажа — `server/internal/ai/ai.go`. Сервер стучится в
  Ollama по HTTP (`localhost:11434`), прогревает модель фоном при старте;
  при недоступности/таймауте (30 сек на генерацию, ожидание слота отдельно)
  падает на шаблонную реплику из FSM — **игра никогда не виснет и не
  остаётся без ответа NPC**, даже если Ollama не запущена.
- **Клиент**: диалог с NPC — полноценное окно чата (`#npc-dialog` в
  `main.js`), открывается по `E` рядом с NPC, игрок печатает свои вопросы
  текстом (а не фиксированная фраза), `Esc` закрывает диалог (не паузу,
  если диалог открыт).
- Протокол сообщений — см. `PROTOCOL.md`.

## 3. Подгрузка мира и требование 10%

Сервер отдаёт `chunk_data` только текущей комнаты: описание комнаты, NPC
и минимальные данные соседей. База фактов не передаётся списком — реплики
приходят по одной через `npc_talk` → `npc_response`. В сцене остаётся одна
комната. `world.js` не кеширует GLB: при выходе отменяет fetch, освобождает
геометрию, материалы, текстуры, ImageBitmap и скелеты. Незавершённый parse
дожидается освобождения перед загрузкой следующей комнаты. Fetch использует
`cache: "no-store"`, соседние GLB не загружаются. HUD показывает загрузку/ошибку,
движение заблокировано до готовности модели. Постоянное небо не является чанком.
Одна комната из десяти — ограничение по количеству; ≤10% по байтам не гарантируется,
поскольку размеры моделей различны. Требуется отдельное измерение объёма.

У `Room` есть необязательные `modelScale`, `radius`, `spawn`, `doors` и
`collision` (`"walkmesh"` включает клиентскую коллизию по GLB во всех комнатах).
Все комнаты сохраняют авторский масштаб 1:1. Двери учитывают высоту камеры,
поэтому галерея не активирует переходы первого этажа. При входе камера
разворачивается внутрь отсека, клиент отправляет позицию обычным `move`.
Формат сетевых сообщений не изменён; поле `collision` аддитивное.

Все 18 сторон проёмов имеют процедурные раздвижные двери (doors.js),
создаваемые по room.doors. Начальное состояние закрыто; E в пределах 2.5 м,
глядя на дверь, открывает/закрывает её. Готовность прохода наступает после
анимации открытия; закрытая дверь блокирует движение и chunk_request.
Нельзя закрывать дверь, стоя в проёме. При переходе/выгрузке все двери
закрываются после успешного перехода на сервере (если проём свободен). Дверь рядом имеет приоритет
E перед NPC; подсказка показывает действие и назначение. Проверка высоты
исключает взаимодействие с нижними дверями с галереи.
Состояние дверей общее на сервере для пары связанных комнат. Клиент отправляет
door_set, сервер проверяет дистанцию и занятость проёма любым игроком.
При уходе игрока двери закрываются для всех; занятые проёмы ждут освобождения.
При входе применяется актуальный серверный snapshot, а не локальный reset.
GLB не менялись: у хаба штатные створки скрываются только в runtime, рамы
и вывески сохраняются; в проёмах стоят новые объекты. Декоративные сегменты
`Hull / lower dado seam`, пересекающие подключённые проёмы, скрываются
перед сборкой коллизии, чтобы поперечная планка не блокировала проход.
Ограждения лестницы и галереи сохраняются.
Створки перекрывают проём с запасом 0.26 м с каждой стороны, с перехлёстом
по центру; высота 2.8 м в lobby и 3.12 м в отсеках. За каждой дверью —
закрытый коридор глубиной 3 м: пол, стены, потолок, свет и торцевой
bulkhead. Переход в соседнюю комнату срабатывает в центре коридора, на глубине 1.5 м,
до торцевой стены. Пол и оболочка коридоров включены в коллизию;
подгружается по-прежнему только текущая комната. Потолок коридора начинается
на 0.18 м за плоскостью двери, стены — от плоскости двери, чтобы не закрывать
таблички. Штатные plaque/room label хаба вынесены вместе на 0.2 м внутрь lobby.

Космический фон общий для всех комнат: `client/src/sky.js` создаётся один
раз, отдельно от чанков. Небо рендерится отдельной камерой без перемещения,
затем очищается только depth buffer и рисуется комната. Оно следует направлению
взгляда, но не позиции игрока: переходы не сдвигают звёзды, Землю и Луну.
Звёздное поле детерминированное; туманность, континенты/облака Земли, атмосфера
и кратеры Луны генерируются локально кодом. Никаких новых загрузок или изменений
существующих моделей/текстур не требуется. Небо видно через существующие
проёмы и прозрачные поверхности; непрозрачные стены по-прежнему закрывают его.

### Уборщики Roomba

В каждой комнате два серверных уборщика из `/models/roomba.glb` (ширина 0.48 м).
Сервер симулирует их движение 10 раз в секунду по графу свободного пола
`world-data/roomba-nav.json`, выбирает случайные маршруты/паузы, скорость
0.38 м/с; учитывает других уборщиков и всех игроков комнаты. Граф подготовлен
из GLB офлайн скриптом `cd client; node scripts/build-roomba-navigation.mjs`:
проверки пола/низких препятствий/NPC, запрет дверных зон и лестниц, шаг сетки
0.5 м с проверкой соединяющих отрезков каждые 5 см. После замены геометрии
комнат или позиций NPC граф следует пересоздать. Go валидирует граф при старте.
Навигационный граф не отправляется клиентам. roombas.js только создаёт GLB-клоны
и интерполирует серверные позы; локального RNG для движения больше нет.
Модели выгружаются с текущей комнатой. Состояние дверей и уборщиков хранится
в памяти сервера, не в SQLite, и сбрасывается при перезапуске.

Сервер отправляет `room_state {state:{room,revision,doors,roombas}}` только
игрокам текущей комнаты; `welcome`/`chunk_data` также содержат `state`.
Клиент отбрасывает старые revision и сообщения не своей комнаты, сохраняет
последний snapshot во время загрузки GLB. Форматы обновляются вместе — нужен
перезапуск Go и обновление всех клиентов. `chunk_request` проверяет общую
открытую дверь и нахождение игрока у центра коридора.

## 4. Авторизация, HTTPS и персистентность

- **Полные аккаунты** с паролем: `POST /api/register {name, password}` (bcrypt-
  хеш, 409 если имя занято) и `POST /api/login {name, password}` (401 на
  неверный пароль/несуществующее имя, выдаёт новый токен). `playerId`
  стабилен для аккаунта — не пересоздаётся при каждом входе, как раньше.
  Подробности — `PROTOCOL.md`.
- **Сервер только на HTTPS/WSS** — сам генерирует свой локальный CA +
  подписанный им серверный сертификат при первом запуске
  (`server/cmd/server/tls.go`), SAN покрывает `localhost` + все текущие
  локальные IP. Без импорта CA на клиенте — обычное предупреждение браузера
  один раз; с импортом (`docs/https-local-ca.md`) — чисто, без
  предупреждений. Подробности — `PROTOCOL.md` → "HTTPS".
- WS (`/ws?token=...`) проверяет токен **до** апгрейда соединения.
- Состояние игрока (позиция, текущая комната) и память NPC
  (`player_id, npc_id, fact_id → told_at`) живут в SQLite
  (`server/station.db`, в `.gitignore`, пересоздаётся при первом запуске).

## 6. Как запустить (дев-режим, два терминала)

```bash
# терминал 1 — сервер
cd server
go run ./cmd/server
# слушает https://:8080 (самоподписанный сертификат генерируется сам при
# первом запуске), читает ../world-data, пишет ./station.db

# терминал 2 — клиент
cd client
npm install   # один раз
npm run dev
# откроет Vite dev server (обычно :5173), /api и /ws проксируются в Go на :8080 (HTTPS)
```

При первом заходе на `https://localhost:8080` (или на адрес сервера) браузер
покажет предупреждение о самоподписанном сертификате — "Дополнительно" →
"Перейти на сайт", один раз. См. `PROTOCOL.md` → раздел "HTTPS".

Для офлайн-демо собрать клиент и раздавать статикой с самого сервера:

```bash
cd client && npm run build       # кладёт файлы в client/dist
cd ../server && go build -o server.exe ./cmd/server
./server.exe                     # теперь раздаёт и API, и статику на https://:8080
```

Переменные окружения сервера (все необязательные, см. `cmd/server/main.go`):
`ADDR` (`:8080`), `WORLD_DATA_DIR` (`../world-data`), `DB_PATH` (`./station.db`),
`CLIENT_DIST_DIR` (`../client/dist`), `CERT_DIR` (`.`, куда класть/откуда
читать `cert.pem`/`key.pem`), `OLLAMA_URL` (пусто = выключено),
`OLLAMA_MODEL` (`qwen2.5:7b`).

### Мультиплеер по LAN/WiFi (несколько ноутбуков)

1. На ноутбуке-сервере собери прод-билд и запусти **именно его** (не
   `npm run dev` — см. ниже, почему это важно):
   ```bash
   cd client && npm run build
   cd ../server && go run ./cmd/server
   ```
2. Узнай LAN-IP сервера: `ipconfig` (Windows), ищи адрес вида `192.168.x.x`.
3. На ноутбуках-клиентах открой в браузере `https://<LAN-IP сервера>:8080`
   (именно `https`, не `http`) — больше ничего на клиентских машинах ставить
   не нужно, только браузер. При первом заходе подтвердить предупреждение о
   самоподписанном сертификате (см. `PROTOCOL.md` → "HTTPS").

Клиент использует `window.location.origin` для HTTP/WS во всех режимах.
В проде страницу и API раздаёт Go. В dev и `npm run preview` маршруты
`/api` и `/ws` проксируются Vite в один Go-процесс на `127.0.0.1:8080`
(`client/vite.config.js`). Go всё равно нужно запускать отдельно.
Для LAN без сборки можно запустить Vite с `npm run dev -- --host 0.0.0.0`
на машине сервера и открыть её адрес с портом Vite. Оба процесса должны
работать в одной ОС/WSL-среде, чтобы адрес прокси `127.0.0.1` был общим.

Для демонстрации на одном ПК открыть **один и тот же адрес** в двух окнах,
войти под разными именами и оставаться в одной комнате. HUD показывает число
подключённых игроков в комнате; при входе клиент отходит от занятой точки
появления и разворачивается к ней, чтобы игроки не стояли внутри друг друга.
Разрыв WS виден в HUD. Сборку «отменять» не нужно: `npm run dev` работает
с исходниками независимо от существующего `client/dist`.

### Аватары игроков и бег

Другие игроки отображаются моделью `astronaut-player.glb`.
Один общий шаблон GLB хранится отдельно от комнат; каждый игрок получает
независимый скелет через SkeletonUtils.clone. Перед измерением вызывается
updateMatrixWorld(true), чтобы обновить bindMatrixInverse клонированного
SkinnedMesh. Модель нормализуется внешней группой до высоты 1.6 м, с центром
XZ в позиции игрока и нижней точкой на полу; авторская иерархия сохраняется. При выходе игрока освобождается
его скелет и name tag; геометрия/текстуры остаются у общего шаблона.
В исходнике нет клипов: players.js опускает руки из T-позы и анимирует
плечи, локти, бёдра, колени и стопы процедурно. Плавная интерполяция координат
задаёт направление тела и интенсивность походки; в покое конечности возвращаются
в нейтральную позу. Собственный вид остаётся от первого лица.
WASD — 4 м/с, WASD + любой Shift — 7 м/с с той же коллизией и подшагами.
Бег других игроков определяется по скорости полученных координат; новых полей
WS нет. Стоящий игрок сохраняет последнее направление движения (yaw не передаётся).
Клавиши сбрасываются при потере фокуса, паузе и logout.

## 7. Текущий статус / известные упрощения

Реализован и вручную проверен (лог проверки — в `UPDATES.md`, запись от
момента создания скелета) полный вертикальный срез: логин → WS →
приветствие с чанком → переход между комнатами → диалог с NPC с памятью
(факты не повторяются) → отказ в WS без токена.

**Сознательно упрощено / не сделано — см. `TASKS.md` для деталей:**

- Все девять отсеков доступны через lobby. Коллизия по геометрии включена
  во всех десяти комнатах, также учитываются NPC.
  Проход лестницы и все переходы после этой интеграции ещё не проверялись в игре.
- Интеграция Ollama и FSM уже в `main`; автор AI-ветки сообщил о проверке
  локального API на своей машине. Без `OLLAMA_URL` работает шаблонный FSM.
  На конкретном сервер-ноутбуке нужно подготовить Ollama и модель **заранее, с интернетом**, и
  проверить, что сервер успевает ответить за разумное время под нагрузкой
  нескольких игроков одновременно.
  - АЙ-АЙ, важно: модель должна быть на той же машине, что будет сервером
    на демо, и скачана **до** отключения интернета.
- Все комнаты и все десять экземпляров NPC используют GLB-модели.
  Источники новых моделей — client/public/models/CHARACTER-CREDITS.md.
- Игроки видят друг друга только внутри одной комнаты (это осознанное
  архитектурное решение, не баг: трансляция движений ограничена комнатой
  игрока, иначе broadcast станет дороже и бессмысленнее на малом экране).
- SQLite файл и собранные `dist/`, `node_modules/` — в `.gitignore`,
  не коммитятся.

## 8. Процесс-файлы, которые НЕ являются частью игры

`CONTEXT.md`, `AGENTS.md`, `CLAUDE.md`, `UPDATES.md`, `TASKS.md`,
`PROTOCOL.md` — это рабочие документы команды и ИИ-агентов, не часть
судимого продукта. Они **коммитятся в git**, потому что это единственный
способ синхронизировать состояние между тремя разными ноутбуками и тремя
разными ИИ-инструментами (Claude Code / Codex / Antigravity) — но если
перед сдачей хочется "чистый" репозиторий, их можно удалить или занести в
`.gitignore` в последнем коммите. До этого момента — не трогать.
